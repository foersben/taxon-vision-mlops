\begin{frame}{Storage Engineering}{The 50 TB Trap \& Parquet Columnar Manifests}
    \begin{block}{Overcoming The 50 TB Storage Trap}
        \begin{itemize}\small
            \item \textbf{The Storage Bottleneck:} Storing multi-terabyte citizen-science imagery locally quickly exhausts developer workstation NVMe storage.
            \item \textbf{Zero-Copy S3 Streaming:} Direct chunked streaming from AWS Open Data / iNaturalist S3 mirrors.
            \item \textbf{Columnar Parquet Manifests:} Lightweight \texttt{observations.parquet} indexes millions of records with sub-millisecond predicate filtering.
            \item \textbf{Architectural Decoupling:} Complete separation between immutable remote pixel assets and local structured metadata.
        \end{itemize}
    \end{block}

    \vspace{0.1cm}
    \statusdone

    \script{In large-scale biological vision, downloading 50 terabytes of raw images is impossible for individual developers. Instead of downloading JPEGs, TaxonVision uses lightweight Apache Parquet index manifests. The images remain on remote AWS Open Data S3 buckets, while our local system works with columnar metadata that can be filtered and sliced in milliseconds.}
    \qa{Why use Apache Parquet instead of an SQLite or PostgreSQL database?}{Parquet provides columnar compression, partitioned scanning, and native zero-copy integration with Apache Arrow, PyTorch, and Polars, making it ideal for distributed MLOps pipelines without database server overhead.}
\end{frame}

\begin{frame}{Data Integrity}{Cryptographic Image Hashes in Parquet Manifests}
    \begin{block}{Cryptographic Manifest Schema \& On-The-Fly Verification}
        \begin{itemize}\small
            \item \textbf{Parquet Manifest Schema:} Stores observation UUID, taxon ID, S3 image URL, DarwinCore ranks, coordinates, and open license tags.
            \item \textbf{Cryptographic Validation Hash:} Every observation carries a SHA-256 / MD5 content hash directly in the columnar row.
            \item \textbf{On-The-Fly Integrity Gate:} \texttt{S3Streamer} verifies byte hashes as Apache Arrow batches stream into memory before decoding tensors.
            \item \textbf{Zero-Poisoning Guarantee:} Prevents corrupted, incomplete, or maliciously modified images from entering the training pipeline.
        \end{itemize}
    \end{block}

    \vspace{0.1cm}
    \statusdone

    \script{How do we ensure that an image on S3 hasn't been corrupted or altered over time? Inside our Parquet manifest, every single observation has a cryptographic SHA-256 validation hash stored alongside its S3 URL. When our S3Streamer module streams the image into memory, it checks the SHA-256 hash immediately before decoding. If a single byte is corrupted, the observation is caught and logged instantly.}
    \qa{Does on-the-fly hash verification introduce CPU bottlenecks?}{SHA-256 hashing in hardware-accelerated CPU instructions takes microseconds per image buffer, which is entirely hidden behind network transfer and image decoding latency.}
\end{frame}


\begin{frame}{Data Formats}{Columnar Storage \& In-Memory Layout: Parquet vs. Arrow}
    \begin{block}{Storage and Layout Architectures}
        \begin{itemize}\footnotesize
            \item \textbf{Visual/Conceptual:} Row-oriented (CSV) vs. Columnar on-disk (Parquet) vs. In-memory columnar (Arrow).
            \item \textbf{Apache Parquet (On-Disk):}
            \begin{itemize}
                \item \textit{Why:} Tabular data row-by-row scans unneeded columns. Parquet uses column-by-column Row Groups.
                \item \textit{Encodings:} Dictionary, RLE, Snappy/Zstd.
                \item \textit{Acceleration:} Column projection + Predicate pushdown (skips groups via min/max).
            \end{itemize}
            \item \textbf{Apache Arrow (In-Memory):}
            \begin{itemize}
                \item \textit{Why:} Eliminates serialization when passing tabular data across language boundaries.
                \item \textit{Layout:} Values buffer, validity bitmap, offset buffer.
                \item \textit{Alignment:} Structured for CPU cache lines and SIMD.
            \end{itemize}
        \end{itemize}
    \end{block}

    \vspace{0.1cm}
    \statusdone

    \script{Let's break down the difference between how data is stored on disk and how it exists in memory. Parquet is an on-disk format: instead of storing data row-by-row like a CSV, it stores data column-by-column, allowing us to read only the columns we need, like taxon ID, while skipping the rest. Arrow, on the other hand, is an in-memory layout. It standardizes how tabular data sits in RAM, eliminating costly serialization when we pass data between Python and C++.}
    \qa{What is predicate pushdown in Parquet?}{It is an optimization where the query engine checks the min/max statistics in the Parquet metadata. If our filter is outside that range, the engine skips the entire row group without ever reading the actual data blocks.}
    \qa{Why do we need Arrow if we already have Pandas dataframes?}{Arrow provides a standardized, contiguous memory layout designed for SIMD instructions, whereas traditional Pandas stored strings as scattered Python objects, causing massive cache misses and serialization overhead.}
\end{frame}

    \script{To query this Parquet and Arrow data, we embed DuckDB directly into our Python process. Think of DuckDB as SQLite for analytics. It doesn't run as a separate server, which means there is no network overhead. DuckDB consumes our Arrow buffers natively with zero memory copies. It processes data in morsels of 2048 tuples, keeping everything perfectly sized for the CPU's L1 and L2 caches, resulting in sub-millisecond taxonomic filtering.}
    \qa{Why not use PostgreSQL for filtering observations?}{PostgreSQL requires a separate daemon process, meaning data must be serialized, sent over a network socket, and deserialized. DuckDB runs in-process and queries Arrow buffers directly via shared memory pointers.}
    \qa{What does 'vectorized execution' mean here?}{Instead of processing rows one at a time (tuple-at-a-time), vectorized engines process small batches (vectors) of data at once, reducing loop overhead and allowing the CPU to use SIMD instructions.}

\begin{frame}{Feature Engineering}{Persistent Feature Caching: Mechanics \& Speedup}
    \begin{block}{Visual Data Flow}
        \centering\vspace{0.2cm}
        Raw S3 Image $\to$ Frozen Backbone Forward Pass $\to$ \texttt{embeddings.npy} (\texttt{np.memmap}) $\leftrightarrow$ \texttt{observations.parquet}
        \vspace{0.2cm}
    \end{block}

    \begin{block}{Why it Works (FLOPs \& IOPS)}
        \begin{itemize}\small
            \item \textbf{Egress \& Decompression:} Continuous S3 network egress and JPEG decompression overhead are eliminated after epoch 0.
            \item \textbf{Computational Reduction:} Linear probe epoch FLOPs drop from $\mathcal{O}(N \cdot P_{\text{backbone}})$ (e.g. 86M params) down to convex linear projection $\mathcal{O}(N \cdot D \cdot K)$ ($D \le 1280$, $K=10$).
            \item \textbf{Runtime Impact:} Reduces training runtime from \textbf{4 hours} to \textbf{10 seconds}.
        \end{itemize}
    \end{block}

    \vspace{0.1cm}
    \statusdone

    \script{By caching features persistently, we eliminate the need to repeatedly download and decompress JPEGs from S3 after the first epoch. More importantly, our computational complexity plummets. Instead of passing images through an 86-million parameter backbone every epoch, we perform a simple convex linear projection. This optimization reduces our training runtime from 4 hours down to just 10 seconds.}
    \qa{Why not cache images locally instead of feature embeddings?}{Caching images avoids S3 egress but still incurs JPEG decompression and the massive $\mathcal{O}(N \cdot P_{\text{backbone}})$ forward pass cost per epoch. Caching embeddings eliminates both.}
    \qa{Does this approach work for fine-tuning the backbone?}{No. Persistent feature caching is specifically designed for linear probing or training lightweight heads on top of a frozen backbone. Full fine-tuning requires backpropagating through the backbone every epoch.}
\end{frame}

\begin{frame}{Cache Invalidation}{Multi-Cache Invalidation Matrix: Criteria \& Scenarios}
    \begin{block}{Cache Key Cryptographic Invariant}
        \vspace{-0.2cm}
        \[
        \resizebox{0.95\linewidth}{!}{$\text{Cache Key} = \text{SHA256}(\text{Backbone ID} \,\Vert{}\, \text{Resolution} \,\Vert{}\, \text{Transform Params} \,\Vert{}\, \text{DVC Split Hash} \,\Vert{}\, \text{Chunking Mode})$}
        \]
    \end{block}

    \begin{block}{When Multiple Caches are Required (The Matrix)}
        \begin{enumerate}\footnotesize
            \item \textbf{Backbone Architecture:} ViT (DINOv3, 384-d) vs. Domain ViT (BioCLIP-2, 512-d) vs. Modern CNN (MobileNetV4, 960-d).
            \item \textbf{Input Resolution:} Standard $224 \times 224$ vs. High-resolution fine-grained crop ($384 \times 384$).
            \item \textbf{Preprocessing Modes:} Macro parent scene ($I_{\text{parent}}$) vs. Zero-shot detected child crop ($I_{\text{child}}$).
            \item \textbf{Dataset Partitions:} Independent immutable caches for \texttt{train}, \texttt{val}, and \texttt{test} splits.
        \end{enumerate}
    \end{block}

    \vspace{0.1cm}
    \statusdone

    \script{Because we cache features, any change to the extraction pipeline necessitates a new cache. We formalise this using a SHA-256 cryptographic invariant that hashes the backbone identity, resolution, transforms, DVC split hash, and chunking mode. This multi-cache invalidation matrix dictates exactly when independent caches must be built---such as when switching from DINOv3 to BioCLIP-2, changing input resolution, or updating dataset partitions.}
    \qa{Why include the DVC Split Hash in the cache key?}{The DVC hash ensures that if the underlying dataset rows or their partition assignments change, the cache is automatically invalidated, preventing data leaks or stale features.}
    \qa{How do we manage the disk space for multiple caches?}{Because the caches are dense NumPy memmap arrays without image overhead, they remain lightweight. We use a Least Recently Used (LRU) policy to evict old caches from the local NVMe drive when approaching the storage limit.}
\end{frame}

\begin{frame}{Storage Engineering}{Object Storage Topology: MinIO vs. DagsHub vs. AWS S3}
    \begin{block}{Three-Tier Object Storage Breakdown}
        \begin{itemize}\small
            \item \textbf{Tier 1: MinIO Local Offline Mock (\texttt{docker-compose.local.yaml}):}
            Runs S3-compatible service locally on developer workstation (\texttt{http://localhost:9000}). Used strictly to unit-test S3 streaming connectors and verify DVC operations offline with zero cloud latency and zero AWS egress fees.
            \item \textbf{Tier 2: DagsHub S3 Endpoint (\texttt{s3://dvc}):}
            Remote Content-Addressed Storage (CAS) for tracked dataset manifests and model checkpoints, authenticated via unified HMAC tokens.
            \item \textbf{Tier 3: AWS Open Data Registry (\texttt{s3://inaturalist-open-data}):}
            Public immutable repository hosting raw citizen-science image archives (terabytes of biodiversity imagery), streamed via zero-copy HTTP range requests without downloading archives.
        \end{itemize}
    \end{block}

    \vspace{0.15cm}
    \statusdone

    \script{\footnotesize Our object storage architecture spans three distinct tiers to balance cost, speed, and immutability. Tier 1 is our local MinIO mock, which lets developers test S3 streaming and DVC sync operations offline without hitting real AWS egress fees. Tier 2 is the DagsHub S3 endpoint, acting as our content-addressed storage for heavy Parquet manifests and model checkpoints. Finally, Tier 3 is the public AWS Open Data Registry, which hosts the massive citizen-science image archives we stream directly during feature extraction.}
    \qa{Why not use AWS S3 for Tier 1 and Tier 2?}{\footnotesize Tier 1 uses MinIO to ensure offline developer autonomy and zero latency during rapid unit-testing. Tier 2 uses DagsHub because it automatically syncs with our MLflow tracking server and provides generous free-tier storage for ML artifacts compared to standard AWS S3 buckets.}
    \qa{How do we handle credentials for all these buckets?}{\footnotesize Tier 1 uses local mock credentials. Tier 3 is publicly readable, requiring no authentication. Tier 2 utilizes short-lived HMAC tokens injected by our CI agent or local environment variables.}
\end{frame}

\begin{frame}{Feature Extraction}{Production Batch Feature Extraction (extract\_features.py)}
    \begin{block}{Batch Representation Caching Pipeline}
        \begin{itemize}
            \item \textbf{Zero-Copy S3 Streaming:} Streams raw images directly from remote storage without local disk exhaustion.
            \item \textbf{Frozen Backbone Inference:} Passes image batches through pre-trained backbones (DINOv3/BioCLIP-2).
            \item \textbf{L2 Normalization:} Extracts unit-norm representations for cosine-distance linear classification.
            \item \textbf{Deterministic Taxon Mapping:} \texttt{build\_taxon\_index\_map} guarantees invariant integer class indexing.
        \end{itemize}
    \end{block}

    \vspace{0.1cm}
    \statusdone

    \script{In \texttt{extract\_features.py}, we execute our batch feature extraction. It connects to S3, loads batches of images through our frozen vision backbone, normalizes the embeddings, and writes them out into compact columnar Parquet files. Crucially, it builds a global taxon index map that deterministically assigns each species an integer index across all train, validation, and test splits. This guarantees that class 42 is always identical across all experiments.}
    \qa{Why use Parquet format for storing numerical feature embeddings?}{Parquet is a compressed columnar format with zero-copy deserialization in Python. Loading a 1 GB Parquet file into memory takes milliseconds compared to slow JSON or CSV parsing.}
\end{frame}
