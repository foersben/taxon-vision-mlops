\chapter{Physical Infrastructure and Data Topology}
\label{ch:infrastructure_topology}

The deployment and continuous training of dense Vision Foundation Models (VFMs) require a balanced trade-off between infrastructure flexibility, execution predictability, and cost efficiency. While managed public cloud environments provide elastic scalability, sustaining persistent GPU instances and high-throughput data transfers for iterative research and continuous integration incurs prohibitive operational expenditures. To establish a cost-effective, self-contained development and execution plane, the platform deploys a dedicated on-premise compute node, combining hardware-level workload isolation with deterministic memory budgeting and transparent storage compression.

\section{Compute Topology and Workload Allocation}

Rather than provisioning continuous, multi-tenant cloud GPU infrastructure, the platform standardises on a dedicated bare-metal host engineered to isolate distinct computational regimes. This architecture amortises infrastructure costs while granting direct control over kernel process isolation, thread pinning, and storage caching.

The central processor features an Intel Core i7-14700K (20 cores, 28 threads: 8 Performance-cores and 12 Efficient-cores), supported by 128~GB of DDR5-5600 system memory. This hybrid core topology allows explicit segregation of heterogeneous workloads:
\begin{itemize}
    \item \textbf{Mathematical Hot Loops:} Compute-intensive operations---such as classification head forward passes, PyTorch gradient calculations, and ONNX Runtime execution---are pinned strictly to the 16 Performance-core threads (\texttt{taskset -c 0-15}), preserving dedicated L2 and L3 cache lines.
    \item \textbf{Asynchronous I/O and Telemetry:} Concurrent background tasks---including Apache Arrow streaming, database indexing, Prometheus scraping, and HTTP ingress handling---are allocated to the 12 Efficient-core threads (\texttt{taskset -c 16-27}), eliminating thread context-switching on critical execution paths.
\end{itemize}

Neural network acceleration is provided by an NVIDIA GeForce RTX 5070 Ti graphics processor equipped with 16~GB of GDDR7 VRAM across a 256-bit memory bus. This provides sufficient Tensor Core throughput and memory bandwidth to execute local batch training, static INT8 post-training quantisation, and sub-15\,ms inference validation without remote latency overhead.

High-throughput storage I/O is backed by a 2~TB PCIe Gen4 NVMe solid-state drive. To maximise read bandwidth when streaming millions of citizen-science image crops, the underlying BTRFS filesystem applies transparent \texttt{zstd:3} compression. However, because BTRFS utilizes Copy-on-Write (CoW) allocation by default, continuous database writes and Data Version Control (DVC) chunk mutations induce significant block fragmentation. To guarantee deterministic read/write performance, all database backends and cache subvolumes are provisioned with the non-CoW attribute (\texttt{chattr +C}), ensuring contiguous physical block allocation across the NVMe bus.

\section{Verified Software Baseline of the Host}
\label{sec:host_baseline}

The host (\texttt{hive-mind}) runs Ubuntu 26.04.1 LTS (codename \textit{resolute}) on a LUKS-encrypted root volume. The proprietary NVIDIA driver in version 615.71.09 is installed, which reports a CUDA user-mode driver of version 13.4. Because the CUDA user-mode driver is backward compatible with older runtime libraries, container images are free to ship an older CUDA runtime. For the RTX 5070 Ti, which belongs to the Blackwell generation (compute capability 12.0), this runtime must however be CUDA 12.8 or newer: earlier PyTorch binary builds contain no kernels for this architecture and abort with a missing-kernel-image error. The CUDA runtime pinned in the dependency lock file is therefore a hard prerequisite of GPU execution rather than a cosmetic detail (see Section~\ref{sec:impl_status}).

\section{GPU Partitioning and Memory Budget}
\label{sec:gpu_partitioning}

Consumer GPUs do not support hardware Multi-Instance GPU (MIG) partitioning. Without further measures, a Kubernetes pod requesting one GPU would therefore lock the entire device and starve every co-located workload. The cluster consequently uses the time-slicing mode of the NVIDIA Kubernetes device plugin, which advertises the single physical GPU as four virtual devices. Time-slicing multiplexes compute cycles but does not isolate memory: all slices share the same VRAM. Isolation is therefore enforced in software, by capping the fraction $f$ of device memory available to the training process through the PyTorch per-process memory fraction. With $f = 0.7$ and a device memory of $M_{\text{VRAM}} = 16\text{ GB}$, the training budget evaluates to
\[
M_{\text{train}} = f \cdot M_{\text{VRAM}} = 0.7 \times 16\text{ GB} = 11.2\text{ GB},
\]
which leaves $M_{\text{VRAM}} - M_{\text{train}} = 4.8\text{ GB}$ for the INT8 ONNX serving process and the display server. The latter reserve is comfortably larger than the serving footprint of $\le 1.6\text{ GB}$ derived in Table~\ref{tab:rag_latency}. To guarantee that heavier secondary models do not violate this envelope, the auxiliary visual language model (\texttt{taxon-vision-vlm}) either scales to zero during active Jenkins GPU training windows or executes quantised VLM synthesis directly on the 16 host P-cores and 128~GB DDR5 system memory, maintaining the active GPU serving footprint strictly $\le 1.6\text{ GB}$ VRAM.

\section{Access Topology and Edge Security}
\label{sec:access_topology}

The host exposes no inbound port to the public internet. Both the CI/CD controller and the operator-facing service are reached through outbound-initiated Cloudflare Tunnels, so that no router port forwarding and no dynamic DNS record is required. A Web Application Firewall rule at the Cloudflare edge restricts the controller hostname (\texttt{jenkins.benjamin-foerster.eu}) to authenticated GitHub webhook deliveries, whilst the operator dashboard and REST API are served live at \texttt{https://taxon.benjamin-foerster.eu} routing directly to Kubernetes NodePort 30080 behind an identity-aware Zero Trust access policy. Remote maintenance after a reboot is possible despite the encrypted root volume, because a minimal SSH daemon (Dropbear) in the initial ramdisk accepts the unlock passphrase before the root file system is mounted.

\section{Cryptographic Storage Economics}
A primary architectural constraint for open-source and low-budget MLOps is data storage costs. The platform standardises on DagsHub as the central management plane, which enforces a 20 GB free-tier storage limit on its DVC remote. This limit is fully viable, provided that the pipeline enforces a strict physical separation between bulk raw observation streams and versioned metadata artefacts.

\subsection{Circumventing the Multi-Terabyte Storage Trap}
The raw citizen-science image corpora hosted on AWS Open Data registries collectively span tens of terabytes (an operational scale colloquially termed the ``50 TB trap''). Mirroring this bulk volume locally or to a Git-tracked remote would be financially and computationally unviable. The system explicitly avoids this through zero-duplication streaming: ingestion pipelines stream raw TAR archives directly from AWS Open Data into memory via zero-copy Apache Arrow buffers.

Rather than storing the raw images, DVC tracks cryptographically validated Parquet index manifests. These lightweight tabular files contain observation IDs, DarwinCore taxonomic metadata, source URLs, and SHA-256 validation hashes. As an illustrative sizing calculation, an Apache Parquet manifest indexing 10 million distinct biological observations requires under 300 MB of storage due to columnar dictionary encoding.

\subsection{Bounded Exemplar Storage Mathematics}
For localised visual retrieval, the Vision RAG architecture curates a bounded Reference Exemplar Catalogue, constrained by policy to at most 50 validated environmental crops per species.

To demonstrate the storage envelope, we model an illustrative production scenario spanning 2,000 baseline taxa (yielding 100,000 curated images). Assuming an empirical compression target of approximately 45 KB per WebP crop (with a conservative 60 KB variance ceiling), the exemplar storage footprint evaluates as:
\[
\text{Storage}_{\text{Exemplars}} = 100{,}000 \text{ images} \times 45 \text{ KB} = 4{,}500{,}000 \text{ KB} \approx 4.5 \text{ GB}
\]
Furthermore, dynamic INT8 quantised ONNX model checkpoints typically range from 20 MB to 350 MB each depending on backbone parameter counts. Retaining a rolling buffer of production release candidates requires under 2.0 GB.

Under these illustrative assumptions:
\begin{align*}
\text{Storage}_{\text{Total}} &= 300 \text{ MB (Manifests)} + 4.5 \text{ GB (Exemplars)} \\
&\quad + 2.0 \text{ GB (ONNX Models)} + 1.5 \text{ GB (DVC Churn)} \approx 8.3 \text{ GB}
\end{align*}
This 8.3 GB peak allocation (or 9.8 GB under peak 60 KB compression ceiling) operates well within the DagsHub 20 GB free-tier allowance, leaving ample headroom for active learning annotations.

\subsection{In-Cluster Object Storage: SeaweedFS Architecture and Multi-Remote Topology}
\label{sec:seaweedfs_topology}

Whilst DagsHub acts as the external Git and DVC synchronisation mirror, high-throughput training and iterative inference loops cannot endure public internet round-trip latencies for ephemeral or high-volume intermediate data. Historically, early prototypes relied upon localised MinIO instances; however, architectural evolution and licensing constraints necessitated an absolute migration to \textbf{SeaweedFS} (\texttt{chrislusf/seaweedfs:latest}), licensed under the permissive \textbf{Apache~2.0} standard.

\subsubsection{Licensing Imperatives and Community Sustainability}
The containerised distribution of upstream MinIO transitioned to the Affero General Public License (AGPLv3), creating severe operational friction for downstream academic and commercial deployments. Following upstream Docker Hub repository purges, community continuity forks (such as Pigsty Silo) offer temporary respite. However, SeaweedFS eliminates all copyleft exposure through an unencumbered Apache~2.0 licence, ensuring complete sovereign control over data plane operations without legal ambiguity.

\subsubsection{The Small-File Bottleneck and Haystack/Needle Mechanics}
In deep vision pipelines, storage workloads exhibit extreme bimodal variance: Pipeline~1 produces heavy, multi-megabyte dense tensor matrices (stratified embedding splits under \texttt{data/embeddings/}, 50--500~MB), whilst Pipeline~2 requires rapid nearest-neighbour retrieval over $N = 100{,}000$ compressed visual exemplar crops ($s \approx 45\text{ KiB}$).

On conventional POSIX filesystems (such as standard ext4, XFS, or Copy-on-Write BTRFS), each individual file requires an independent inode allocation. Under continuous multi-worker streaming, reading $N$ small objects introduces the high-latency phenomenon known as \textit{disk-seek death}:
\[
T_{\text{read}} = \sum_{i=1}^{N} \left( t_{\text{inode\_lookup}}(i) + t_{\text{seek}}(i) + \frac{s_i}{B_{\text{NVMe}}} \right),
\]
where $t_{\text{inode\_lookup}} + t_{\text{seek}} \gg \frac{s_i}{B_{\text{NVMe}}}$, causing bus starvation and driving p95 retrieval latency beyond 30~ms.

SeaweedFS solves this structural bottleneck by adopting the Facebook Haystack needle-packing architecture. Individual observation crops are appended sequentially into contiguous, pre-allocated 32~GB volume files (\texttt{.dat}), whilst needle keys, physical byte offsets, and sizes are maintained within an in-memory compact hash index (\texttt{.idx}):
\[
\text{Memory}_{\text{Index}} = N \times 16 \text{ bytes} \approx 100{,}000 \times 16\text{ B} = 1.6\text{ MB}.
\]
Consequently, object lookups require exactly $O(1)$ disk seeks, enabling SeaweedFS to sustain sub-$2\text{ ms}$ p95 read latencies on host NVMe storage under saturated 4~KiB random-read workloads.

\subsubsection{Consolidated Cluster Daemon and Dynamic Bucket Provisioning}
In Kubernetes, SeaweedFS is deployed as a consolidated, lightweight single-container daemon executing \texttt{weed server -dir=/data -s3 -s3.port=8333 -s3.config=/etc/seaweedfs/s3.json -volume.max=20}. This encapsulates four coordinated internal subsystems within an active memory envelope of approximately 80~MB RAM:
\begin{enumerate}
    \item \textbf{The Master Service (port 9333):} Manages topology assignment, volume growth, and leader election.
    \item \textbf{The Volume Server (port 8080):} Directly executes sequential needle read/write operations against the host NVMe filesystem.
    \item \textbf{The Filer Engine (port 8888):} Maintains a hierarchical directory tree and metadata catalog backed by embedded LevelDB.
    \item \textbf{The S3 REST Gateway (port 8333):} Translates AWS S3 Signature Version 4 (SigV4) API calls into high-performance Filer entries.
\end{enumerate}

Unlike legacy MinIO configurations that mandate an auxiliary sidecar container executing asynchronous \texttt{mc mb} loops to initialise buckets, SeaweedFS dynamically auto-provisions bucket roots upon receiving valid authenticated S3 \texttt{CreateBucket} requests or pre-initialises buckets declaratively via a container lifecycle hook targeting the local Filer HTTP endpoint:
\begin{minted}{bash}
wget -q -O - --post-data="" "http://127.0.0.1:8888/buckets/taxon-dvc-cache/?op=mkdir"
wget -q -O - --post-data="" "http://127.0.0.1:8888/buckets/triage-queue/?op=mkdir"
\end{minted}

\subsubsection{Filesystem Invariants and Multi-Remote Routing}
To prevent physical block fragmentation across the NVMe bus, the underlying persistent directory (\texttt{/var/lib/taxon-vision/seaweedfs}) is mounted onto a dedicated BTRFS subvolume configured with the \texttt{NOCOW} (\texttt{chattr +C}) attribute. Furthermore, because SeaweedFS volume daemons lock underlying volume data files (\texttt{.dat}), the Kubernetes Deployment enforces \texttt{strategy.type: Recreate}. This prevents multi-attach volume lock collisions on single-node NVMe persistent volumes during rolling updates by guaranteeing that the terminating pod releases file locks before the replacement pod initialises. Automatic volume compaction runs in the background whenever deleted needle space exceeds 30\%, reclaiming disk space without interrupting live inference loops.

DVC synchronisation is partitioned strictly across two distinct remotes:
\begin{itemize}
    \item \textbf{The In-Cluster High-Throughput Remote (\texttt{local-seaweedfs}):} Targeting \texttt{s3://taxon-dvc-cache} at \texttt{http://seaweedfs.taxon-vision.svc.cluster.local:8333}. Dedicated to multi-gigabyte embedding caches (\texttt{train\_embeddings.pt}, \texttt{val\_embeddings.pt}, \texttt{cal\_embeddings.pt}, \texttt{test\_embeddings.pt}), enabling zero-egress, wire-speed caching for Bayesian hyperparameter optimisation sweeps.
    \item \textbf{The Public Lineage Remote (\texttt{origin}):} Targeting \texttt{s3://dvc} at DagsHub. Dedicated to release model checkpoints (\texttt{head.pt}) and INT8 quantised runtimes (\texttt{model\_int8.onnx}).
\end{itemize}

\subsection{In-Cluster Ephemeral Upload Cache: Redis Architecture and Split-Brain Elimination}
\label{sec:redis_upload_cache}

While static assets and multi-gigabyte training tensors reside in SeaweedFS and DagsHub, the production serving layer introduces an ephemeral data plane requirement: holding raw uploaded image bytes across multi-step user interaction workflows.

\subsubsection{Multi-Pod Split-Brain in Interactive Explainability}
In the TaxonVision dashboard, an operator uploads an unlabelled organism crop to obtain conformal prediction sets via \texttt{POST /predict}. If the classification result exhibits epistemic ambiguity (e.g. $|\hat{C}| > 1$), the operator clicks ``Explain CAM'' in the web UI, which triggers a secondary request to \texttt{POST /explain} supplying the SHA-256 image hash.

In a horizontally scaled serving topology with two or more FastAPI pods behind Traefik ingress, an in-memory image cache (\texttt{OrderedDict} with threading locks) causes a catastrophic \textit{multi-pod split-brain}:
\begin{enumerate}
    \item \textbf{Pod 1} processes the initial \texttt{/predict} upload, storing the decompressed image array in its private process heap memory.
    \item Traefik's round-robin or least-connections load-balancing algorithm routes the subsequent \texttt{/explain} call to \textbf{Pod 2}.
    \item \textbf{Pod 2} inspects its local process RAM, fails to locate the hash, and returns HTTP 422 Unprocessable Entity (``Image not found or expired'').
\end{enumerate}

\subsubsection{Redis Ephemeral Cache Implementation}
To resolve this split-brain without imposing sticky sessions or heavy cloud object store latency, the cluster provisions an in-cluster \textbf{Redis Ephemeral Cache} (\texttt{redis-ephemeral:6379}). The cache architecture enforces strict resource and lifecycle bounds:
\begin{itemize}
    \item \textbf{Memory Envelope and Eviction:} Memory is capped at 64~MB with \texttt{maxmemory-policy allkeys-lru}. Because each raw JPEG/WebP crop averages 45--60~KB, a 64~MB envelope comfortably buffers over 1,000 concurrent active operator sessions.
    \item \textbf{Deterministic Expiration:} Raw image bytes are written via atomic \texttt{SETEX} with a 900-second (15-minute) time-to-live:
    \[
    \texttt{redis.setex(f"img:\{image\_hash\}", 900, raw\_bytes)}
    \]
    This guarantees zero memory leak accumulation without requiring background thread garbage-collection loops in Python.
    \item \textbf{Sub-Millisecond Retrieval:} Any serving pod can retrieve the cached image payload in sub-millisecond latency ($t_{\text{redis}} < 0.5\text{ ms}$ over localhost loopback/cluster SDN), enabling Pod~2 to compute Grad-CAM overlays seamlessly.
    \item \textbf{Graceful Degradation:} If the Redis service becomes temporarily unreachable, the \texttt{UploadCache} component automatically falls back to local in-memory caching and logs a structured warning, ensuring service resilience during cache restarts.
\end{itemize}
