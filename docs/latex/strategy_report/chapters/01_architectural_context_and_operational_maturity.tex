\chapter{Architectural Context and Operational Maturity}
\label{ch:context_maturity}

The transition from localised machine learning prototypes to global ecological monitoring platforms requires fundamentally re-evaluating how systems manage scale, uncertainty, and regulatory compliance. Accordingly, this chapter establishes the operational baseline for the TaxonVision-MLOps architecture. It formalises the scale of citizen-science data streams, identifies the failure modes of unmanaged workflows, and defines the phased Machine Learning Operations (MLOps) maturity framework required to sustain a production environment.

\section{Data Topography and Open-Access Mandates}
Global biodiversity portals such as iNaturalist and the Global Biodiversity Information Facility (GBIF) aggregate continuous streams of species observations worldwide. Combined, these ecosystems host an estimated 270 million raw observations (as of public registry reporting in 2024 -- 2026), of which roughly 170 million have achieved ``research grade'' status through community validation. Processing this high-volume stream requires strict cryptographic and legal compliance safeguards right at the ingestion edge.

In order to enforce open-access mandates, the ingestion engine inspects incoming observation metadata headers prior to staging objects locally. A cryptographic licence filtering module evaluates record metadata against allowed open-access definitions, thereby enforcing strict inclusion filters for Creative Commons Zero (CC0), Creative Commons Attribution (CC-BY), and Creative Commons Attribution-NonCommercial (CC-BY-NC). Any incoming observation tagged with restrictive, no-derivative (\texttt{CC-BY-ND}), or copyleft/share-alike variants (\texttt{CC-BY-SA}) is explicitly dropped at the network boundary to eliminate viral licensing constraints on derived model weights. Furthermore, to comply with GBIF and iNaturalist scientific lineage requirements, an automated attribution preservation mechanism extracts observation GUIDs, contributor ORCIDs, and original licence headers, serialising them alongside downstream feature vectors in order to maintain absolute lineage traceability.

\section{The Operational Bottleneck in Biodiversity Monitoring}
Fine-grained biological species identification at a global scale represents a formidable computational challenge. Citizen-science platforms generate continuous, high-volume streams of unstructured visual observations across highly variable environments. Historically, translating these raw field photographs into verified ecological intelligence has been severely constrained by fragile, ad-hoc machine learning engineering.

When predictive models are trained in isolated Jupyter notebooks -- a state defined as Level 0 (Manual Process) maturity -- they already suffer from non-reproducible software environments, untracked parameter drift, and silent degradation under natural distribution shifts. In an operational setting, these isolated scripts break down entirely during the handoff between data science and deployment teams. This renders the system incapable of sustaining continuous updates or scaling to support thousands of distinct taxa.

\section{The TaxonVision Operational Maturity Framework}
To process citizen-science visual streams reliably, the TaxonVision-MLOps architecture enforces a structured paradigm shift. Rather than relying solely on traditional MLOps reference architectures, we adopt Google's foundational 3-level MLOps spectrum (Levels 0 -- 2: Manual, Automated Pipeline, and CI/CD) and extend it into a tailored 5-Tier Operational Maturity Framework. By introducing Level 3 (Feedback \& Active Learning) and Level 4 (Epistemic Safety), the platform bridges standard deployment automation with mathematical coverage guarantees required for ecological monitoring.

\section{Tri-Plane Orchestration Matrix}
\label{sec:tri_plane_orchestration}

A common anti-pattern in MLOps architectures is tool overlap -- attempting to force a single CI runner to handle cron scheduling, or forcing a workflow orchestrator to execute bare-metal GPU builds. The TaxonVision-MLOps platform eliminates ambiguity by enforcing a strict \textbf{Tri-Plane Orchestration Matrix}, cleanly partitioning duties across three specialised engines:
\begin{enumerate}
    \item \textbf{GitHub Actions (Static PR Verification \& Release Plane):} Ephemeral cloud runners executing fast pre-merge verification: Ruff linting, MyPy strict type analysis across 70 source files, Open Knowledge Format (OKF) schema validation, license audits, cognitive complexity bounds ($\le 15$), and fast pytest suites. Upon merge to \texttt{main}, it builds hermetic wheel distributions and multi-arch production container images published to GHCR.
    \item \textbf{Apache Airflow 3 (Stateful Control Plane \& Scheduling):} Deployed as an in-cluster control plane running \texttt{LocalExecutor} backed by PostgreSQL. Airflow is strictly reserved for stateful, cron-scheduled, and event-driven workflows: the hourly prediction drift monitor (\texttt{prediction\_drift\_monitor} DAG), automated retraining coordination (\texttt{model\_retraining} DAG), and bidirectional synchronisation with the Label Studio human annotation workspace. Airflow executes zero heavy machine learning operations itself, maintaining an extremely light operational footprint without requiring CUDA drivers or Python virtual environment overhead in scheduler containers.
    \item \textbf{Jenkins (Bare-Metal GPU Compute Plane):} Deployed on the local bare-metal host, Jenkins manages ephemeral Kubernetes worker pods with exclusive NVIDIA GeForce RTX 5070 Ti access. Jenkins executes the computationally intensive stages of the DVC pipeline: high-throughput Vision Transformer feature extraction, Optuna Bayesian hyperparameter sweeps, and Stage~7 dual holdout evaluation with the Four-Gate Model Promotion Verdict.
\end{enumerate}

\section{Remote-Only Execution Principle}
\label{sec:remote_only}

A further design decision concerns the location at which computation takes place. The developer workstation is deliberately not provisioned for model training. It serves as an authoring, linting and orchestration plane, whereas every training run, hyperparameter search and ONNX compilation is executed on the bare-metal host described in Chapter~\ref{ch:infrastructure_topology}. These jobs are dispatched by the CI/CD controller only after all quality gates have been passed. This principle has three consequences:
\begin{itemize}
    \item \textbf{Reproducibility:} Each run starts from an ephemeral container and a frozen dependency lock file, so that the execution environment cannot drift between runs.
    \item \textbf{Auditability:} The cryptographic dataset hash recorded by DVC is logged to the experiment tracker together with the metrics of every run, which links each model version to the exact data state it was trained on.
    \item \textbf{Resource isolation:} Long-running GPU workloads cannot degrade the interactive responsiveness of the development machine, and they are scheduled alongside the serving workload under an explicit memory budget (Section~\ref{sec:gpu_partitioning}).
\end{itemize}

\section{Normative Architecture and Implementation Status}
\label{sec:normative_status}

This report distinguishes between the normative target architecture and the state of its implementation. Chapters~\ref{ch:infrastructure_topology} to~\ref{ch:hardware_math} describe the target architecture and the mathematical properties it is required to satisfy. The implementation status verified against the code base, including known deviations and open items, is consolidated in Section~\ref{sec:impl_status} of Chapter~\ref{ch:conclusion}.
