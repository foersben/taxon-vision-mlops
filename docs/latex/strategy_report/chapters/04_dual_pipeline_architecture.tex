\chapter{Dual Pipeline Architecture}
\label{ch:dual_pipeline}

A common anti-pattern in machine learning deployments is the monolithic pipeline, where neural network training sequences and data indexing tasks are tightly coupled into a single execution graph. The TaxonVision-MLOps architecture explicitly rejects this model. Instead, as visualised in the comprehensive architectural overview following Chapter 1, it establishes a dual-pipeline topology that decouples the weight-centric classification engine from the data-centric Multimodal Knowledge Graph (MMKG). These pipelines maintain independent lifecycles, converging exclusively at the inference serving boundary.

\section{Asymmetric Iteration and Execution Decoupling}
\label{sec:decoupling}

The necessity for architectural decoupling stems directly from the fundamentally asymmetric nature of biological modelling operations.

\textbf{Pipeline 1: The Classification Engine.} The primary neural backbone (for example, an optimised BioCLIP-2 \cite{stevens2024bioclip} or DINOv3 transformer) is computationally expensive to train but relatively static in production. Refining its weights using Class-Balanced Loss \cite{cui2019classbalanced} requires intensive GPU Tensor Core utilisation, distributed gradient synchronisation, and static ONNX Post-Training Quantisation (PTQ) calibration. However, once an optimal checkpoint is compiled, the model architecture may remain unchanged for weeks or months.

\textbf{Pipeline 2: The Taxonomic MMKG.} Conversely, the underlying citizen-science data stream is highly volatile. The pipeline must ingest continuous drops of new iNaturalist research-grade observations. More critically, biological taxonomies are frequently subjected to scientific realignments -- species are split into novel taxonomic branches or lumped together under unified nomenclature. Pipeline 2 is an I/O-bound vector-indexing workflow responsible for parsing DarwinCore Parquet manifests, extracting zero-shot organism crops, filtering open-source licences, and appending dense embeddings to the Hierarchical Navigable Small World (HNSW) graph.

Forcing Pipeline 1 to re-execute a heavy neural network training sweep merely because Pipeline 2 updated an exemplar image for a specific beetle species wastes immense computational resources. Furthermore, physically separating these domains enforces strict failure isolation. If a malformed DarwinCore archive from an upstream provider induces a schema violation, Pipeline 2 will halt securely. However, Pipeline 1 remains entirely unimpeded, preserving our ability to compile, test, and deploy critical hot-fixes to the classification logic.

In order to transition from manual experimentation to a Level 3 MLOps deployment, the independent pipelines must be strictly governed by Continuous Integration and Continuous Deployment (CI/CD) triggers.

Two cooperating layers implement these triggers. When engineers push codebase modifications to the central repository, GitHub Actions executes lightweight static analysis (Ruff, MyPy), open-licence auditing, Open Knowledge Format (OKF) validation, unit and conformal test suites, and cognitive complexity scanning via \texttt{complexipy}. To validate serving endpoints during pull request review, the runner hydrates DVC model checkpoints directly from DagsHub. Upon merge to \texttt{main}, GitHub Actions automatically packages the production container image, hydrates promoted model checkpoints from DagsHub DVC, and publishes multi-tagged images to GitHub Container Registry (\texttt{ghcr.io/foersben/taxon-vision-mlops:latest}). In parallel, a signed GitHub webhook reaches a self-hosted Jenkins controller through an outbound-only Cloudflare Tunnel. The controller owns no persistent executors of its own: it schedules each build across a bifurcated, two-pod hybrid execution topology inside the k3s cluster of the bare-metal host:
\begin{enumerate}
    \item \textbf{\texttt{jenkins-cpu-runner} (Lightweight Quality Gate):} Ephemeral CPU-only pod (1 core, 2~GB RAM) executing fast static verification: Ruff linting, MyPy strict typing across all 70 source files, 203 automated pytest tests, OKF frontmatter validation, and license audits. Pod execution employs a defensive \texttt{cleanWs} workspace guard to guarantee zero state leakage across builds.
    \item \textbf{\texttt{jenkins-gpu-runner} (Heavy Compute Workload):} Dedicated GPU pod requesting an isolated NVIDIA GeForce RTX 5070 Ti allocation (16~GB VRAM) under \texttt{imagePullPolicy: IfNotPresent} to eliminate redundant multi-gigabyte container pulls over the WAN. This pod executes CUDA feature extraction, Optuna Bayesian hyperparameter sweeps, and INT8 post-training quantization.
\end{enumerate}
Credentials for the tracking infrastructure, in particular the DagsHub access token, are held in the Jenkins credential store and are exposed to the build as environment variables for the duration of the run only. Production traffic is routed via Traefik v3.1 Ingress, supporting dynamic 80/20 canary traffic splits between \texttt{Production} and \texttt{Challenger} deployments, coupled with Sablier middleware for automated scale-to-zero resource management during idle operational intervals.

\subsection{Two-Stage Distribution and Provenance Attestation}
\label{subsec:release_distribution}

In addition to containerised cluster deployments, standard library distribution mandates a hardened Python wheel and source distribution pipeline. A dedicated two-stage GitHub Actions release workflow (\nolinkurl{.github/workflows/release.yaml}) governs tagged releases (\texttt{v*}):
\begin{enumerate}
    \item \textbf{Stage 1: Hermetic Package Compilation and Verification:} Executing within a dedicated CPU Pixi environment (\texttt{ci-dev}), the runner builds the distribution wheel and source tarball using \texttt{pip wheel --no-deps}. Crucially, the pipeline enforces strict dependency hygiene via \texttt{pip check}, validates runtime importing in an isolated environment, and computes cryptographic SHA-256 hashes across all build payloads.
    \item \textbf{Stage 2: Release Publication and Cryptographic Attestation:} Upon successful gate completion, the workflow generates a formal GitHub Release, attaching the verified wheel, source archive, and SHA-256 checksum manifest to guarantee end-to-end supply chain provenance.
\end{enumerate}

As the training pipeline initialises, it is specified to bind the MLflow telemetry to the exact Git commit that triggered the run, thereby ensuring cryptographic provenance between the source code and the resulting model weights:
\begin{minted}{python}
mlflow.set_tag("git.commit", os.environ.get("GIT_COMMIT"))
\end{minted}

Crucially, the CI/CD pipeline enforces an automated epistemic safety gate prior to deployment. Before any compiled model is allowed to enter the registry, a standalone invariant test loads the candidate ONNX graph and evaluates it against a holdout calibration dataset. The script formally asserts that the empirical marginal coverage of the Split Conformal Prediction set, $|C|$, meets or exceeds the mathematical bound $1 - \alpha$ (for example, $95\%$ coverage, where $\alpha=0.05$). If the empirical coverage falls below this strict threshold, the pipeline throws a fatal assertion error, blocking the Git merge and effectively preventing the uncalibrated model from reaching production.

If the safety gate is cleared, the system programmatically interacts with the MLflow API. The candidate is compared with the model carrying the \texttt{Production} alias by validation Macro PR-AUC: a better candidate is marked as \texttt{Challenger}, whereas an inferior one is archived. The promotion of a \texttt{Challenger} to \texttt{Production} remains a deliberate step after deployment testing, so that at most two competing models are active at any time:
\begin{minted}{python}
client.set_registered_model_alias(
    name="taxon_vision_classifier",
    alias="Challenger",
    version=mv.version,
)
\end{minted}

\section{Automated Training on the Main Branch: The Epistemic Diamond DAG}
\label{sec:main_training}

On the main branch, the CI/CD pipeline continues beyond the quality gates and executes the complete 7-stage Epistemic Diamond DAG on the bare-metal host. The stages are strictly governed by parameter definitions in the canonical root \texttt{params.yaml} and implemented as first-class CLI entrypoints within \texttt{src/taxon\_vision/pipelines/}. The execution lineage forms a closed diamond topology that guarantees reproducible data-to-model provenance:
\begin{enumerate}
    \item \textbf{Stage 1: Ingestion (\texttt{src/taxon\_vision/pipelines/ingest.py}):} Queries research-grade citizen-science observation records across catalogued taxa via \texttt{INatAPIClient}, emitting the initial raw manifest \nolinkurl{data/manifests/raw_manifest.parquet}.
    \item \textbf{Stage 2: Licence Audit (\texttt{src/taxon\_vision/pipelines/audit\_license.py}):} Validates observation records against Rule 05 Open License constraints, filtering non-compliant items and saving verified entries with full photographer attribution to \nolinkurl{data/manifests/dataset_manifest.parquet} and \nolinkurl{reports/license_audit.json}.
    \item \textbf{Stage 3: Feature Extraction (\texttt{src/taxon\_vision/pipelines/extract\_features.py}):} Lazily streams observation imagery from AWS S3, passing images through the frozen foundation backbone (e.g., DINOv3 with $d=384$, or BioCLIP-2 with $d=512$). It partitions representations into four discrete, stratified tensor files under \nolinkurl{data/embeddings/}: \nolinkurl{train_embeddings.pt} (70\%), \nolinkurl{val_embeddings.pt} (10\%), \nolinkurl{cal_embeddings.pt} (10\%), and \nolinkurl{test_embeddings.pt} (10\%). This diamond fan-out eliminates data leakage between training, calibration, and final holdout benchmarking.
    \item \textbf{Stage 4: Head Training (\texttt{src/taxon\_vision/pipelines/train.py}):} Trains a lightweight linear classification head on \nolinkurl{train_embeddings.pt} and \nolinkurl{val_embeddings.pt} using Class-Balanced Loss ($E_n = \frac{1-\beta^n}{1-\beta}$) and Bayesian hyperparameter sweeps via Optuna, outputting \nolinkurl{models/checkpoints/head.pt} and \nolinkurl{reports/train_metrics.json}.
    \item \textbf{Stage 5: ONNX Export \& PTQ (\texttt{src/taxon\_vision/pipelines/export\_onnx.py}):} Compiles the PyTorch classifier into two specialised ONNX execution graphs:
    \begin{enumerate}[label=(\alph*)]
        \item \textbf{End-to-End Dual-Output Graph (\nolinkurl{models/checkpoints/model_int8.onnx}):} Ingests raw normalised image tensors ($\mathbb{R}^{3 \times 224 \times 224}$) and emits both unnormalised logits $f(x) \in \mathbb{R}^K$ and penultimate feature embeddings $z(x) \in \mathbb{R}^D$ in a single forward pass, quantised via INT8 Post-Training Quantisation (PTQ).
        \item \textbf{Dedicated Linear Head Graph (\nolinkurl{models/checkpoints/head_int8.onnx}):} Ingests pre-computed embedding vectors ($z \in \mathbb{R}^D$) directly and emits logits $f(z) \in \mathbb{R}^K$. This enables sub-millisecond evaluation ($t_{\text{head}} < 0.2\text{ ms}$) during active learning query loops and vector triage without invoking the heavy Vision Transformer backbone.
    \end{enumerate}
    \item \textbf{Stage 6: Split Conformal Calibration (\texttt{src/taxon\_vision/pipelines/calibrate.py}):} Evaluates the holdout calibration partition \nolinkurl{data/embeddings/cal_embeddings.pt} through \nolinkurl{model_int8.onnx}. It calculates the empirical non-conformity quantile $\hat{q}_\alpha$ and Helmholtz free energy OOD threshold $\tau_{\text{energy}}$, serialising runtime parameters to \nolinkurl{config/conformal_config.yaml} and \nolinkurl{reports/conformal_metrics.json}.
    \item \textbf{Stage 7: Pareto Evaluation (\texttt{src/taxon\_vision/pipelines/evaluate.py}):} Evaluates candidate backbones against the pristine holdout test partition \nolinkurl{data/embeddings/test_embeddings.pt} using \nolinkurl{model_int8.onnx} and \nolinkurl{config/conformal_config.yaml}. It mathematically verifies the empirical marginal coverage bound ($\ge 1 - \alpha$), calculates p95 latency, throughput, and hardware efficiency profiles (parameter counts, MACs/FLOPs, and peak memory footprint), and writes \nolinkurl{reports/pareto_evaluation.json} and \nolinkurl{docs/assets/pareto_results.json}.
\end{enumerate}
Checkpoints, graphs, and evaluation reports are pushed to DVC remotes, and a rolling restart of the serving deployment (\texttt{imagePullPolicy: Always}) loads the fresh artefacts without interrupting service.

\section{Convergence at the Serving Boundary}
\label{sec:serving_convergence}

The two distinct pipelines exist in absolute isolation until the precise moment of user inference. The FastAPI serving application acts as the convergence node, simultaneously loading the INT8 quantised dual-output ONNX graph from Pipeline~1 into memory, whilst mounting the live HNSW vector index compiled by Pipeline~2.

When a field observation is submitted to the API, it is passed through the fast-path ONNX backbone. Emitting both class logits and dense feature embeddings in a unified forward pass eliminates a redundant second transformer evaluation, directly supplying $z(x)$ for spatial-temporal vector search and drift monitoring. To guarantee epistemic reliability whilst preserving strict latency bounds, the inference engine executes a deterministic 4-tier conformal routing contract governed by the prediction set size $|\hat{C}(X)|$ and top-1 probability $\hat{\pi}_{\max}(X) = \max_y \hat{\pi}_y(X)$:
\begin{enumerate}
    \item \textbf{Decisive Classification ($|\hat{C}(X)| = 1$ with $\hat{\pi}_{\max}(X) \ge \tau_{\text{conf}}$):} The model exhibits high confidence and low epistemic ambiguity. When the top-1 softmax probability meets the operational threshold $\tau_{\text{conf}} = 0.60$, the endpoint dispatches the single predicted taxon immediately, fulfilling the strict sub-$25\text{ ms}$ Service Level Objective (SLO) without activating retrieval overhead.
    \item \textbf{Moderate Ambiguity ($1 < |\hat{C}(X)| \le k_{\max}$, with $k_{\max} = 3$):} The conformal prediction set contains between two and three plausible sibling taxa. The serving engine executes a single-stage filtered HNSW traversal over LanceDB, constrained by the candidate class identifiers and spatio-temporal metadata, and performs Reciprocal Rank Fusion (RRF) over visual exemplar crops with less than $6\text{ ms}$ overhead to deliver a multi-candidate comparative differential to the operator.
    \item \textbf{Severe Ambiguity or Under-Confident Singleton ($|\hat{C}(X)| > k_{\max}$ or ($|\hat{C}(X)| = 1 \land \hat{\pi}_{\max}(X) < \tau_{\text{conf}}$)):} The prediction set exceeds the bound of actionable human differential review, or a singleton set fails the minimum confidence threshold ($\hat{\pi}_{\max} < 0.60$). The query is scheduled for asynchronous multimodal resolution via gRPC to the quantised visual language model (\texttt{taxon-vision-vlm}, based on Qwen2-VL-2B) and persisted locally via \nolinkurl{persist_flagged_observation()} before ingestion into \nolinkurl{triage_queue.lance} on SeaweedFS for expert review.
    \item \textbf{Epistemic Novelty / Complete Abstention ($|\hat{C}(X)| = 0$):} The observed sample violates the conformal coverage boundary, indicating an out-of-distribution observation, unmodelled developmental instar, or extreme sensor degradation. The system executes complete epistemic abstention, bypasses automated classification entirely, executes an unconstrained nearest-neighbour retrieval over the global exemplar space, and dispatches an immediate priority triage alert to human taxonomists.
\end{enumerate}

\section{Low-Latency Interpretability: Forward-Hooked CAM and Decoupled Serving}
\label{sec:cam_shortcut}

Providing diagnostic transparency to human reviewers and field taxonomists requires visual interpretability tools such as Class Activation Mapping (CAM). Whilst gradient-based extensions such as Grad-CAM are standard in offline research, they require a computationally expensive backward pass during inference. Executing gradient backpropagation on a production server introduces an unacceptable $60\text{--}100\text{ ms}$ processing overhead, violates the sub-$25\text{ ms}$ latency Service Level Objective (SLO), and prevents deployment in highly optimised, forward-only runtimes such as INT8 ONNX Runtime.

To achieve visual interpretability without violating strict operational latency constraints, the architecture executes forward-only Class Activation Mapping, tightly integrated into a decoupled, progressive-disclosure serving workflow.

\subsection{Mathematical Formulation and Linear Head Contraction}
\label{subsec:cam_formulation}

The linear classification head $f(z) = W z + b$ parameterises the mapping from an embedding vector $z \in \mathbb{R}^d$ to $K$ unnormalised logits, where $W \in \mathbb{R}^{K \times d}$ denotes the weight matrix. During the initial forward pass, forward execution hooks capture unpooled spatial activation features $A \in \mathbb{R}^{d \times H_{\text{grid}} \times W_{\text{grid}}}$ emitted by the final backbone stage prior to global average pooling. Because the final classification head is linear, the importance weight $w_k^c$ of feature channel $k$ for a target class $c$ is identically the learned weight matrix element $W_{c, k}$.

The class activation map $L^c_{\text{CAM}} \in \mathbb{R}^{H_{\text{grid}} \times W_{\text{grid}}}$ is synthesised through the linear combination
\[
L^c_{\text{CAM}} = \text{ReLU}\left( \sum_{k=1}^d W_{c, k} A^k \right),
\]
where $\text{ReLU}$ discards negative spatial influences to isolate regions that positively support class hypothesis $c$. The resulting two-dimensional activation matrix is min-max normalised and bilinearly upsampled to the native input resolution $(H_{\text{img}}, W_{\text{img}})$. By relying exclusively on forward activations and static linear projection weights, this formulation synthesises high-fidelity spatial saliency heatmaps in under $2\text{ ms}$ on CPU, entirely preserving the forward-only, quantisation-friendly execution paradigm.

\subsection{Vision Transformer Spatial Projection Invariants}
\label{subsec:cam_vit_projection}

Modern vision foundation models (such as DINOv2 \texttt{vit\_base\_patch14\_reg4\_dinov2} or BioCLIP-2) emit flattened token sequences rather than two-dimensional convolutional grids. Specifically, the unpooled feature tensor exhibits the shape $(B, 1 + N_{\text{reg}} + N, d)$, comprising a leading classification token (\texttt{[CLS]}), $N_{\text{reg}}$ optional register tokens introduced to absorb high-norm artefacts, and $N$ spatial patch tokens.

To prevent spatial misalignment or index corruption, the projection subroutine (\nolinkurl{_project_vit_features} in \nolinkurl{src/taxon_vision/inference/cam.py}) enforces strict architectural invariants:
\begin{enumerate}
    \item \textbf{Prefix Token Stripping:} The leading $1 + N_{\text{reg}}$ non-spatial tokens are sliced off and discarded.
    \item \textbf{Square Lattice Assertion:} The remaining token count $N$ must satisfy a perfect square topology, $H_{\text{grid}} = W_{\text{grid}} = \lfloor\sqrt{N}\rfloor$ (e.g., $N = 196$ tokens emitted by a $224 \times 224$ input with patch size $14 \times 14$ yield an exact $14 \times 14$ spatial lattice). Any dimensional mismatch raises a typed \texttt{SaliencyExtractionError}.
    \item \textbf{Tensor Reshaping and Einstein Summation:} The projected token tensor is reshaped to $(B, d, H_{\text{grid}}, W_{\text{grid}})$, after which channel contraction against class weight vector $W_{c, :}$ is evaluated via Einstein summation (\texttt{torch.einsum('bdhw,d->bhw', features, weights)}).
\end{enumerate}
If feature extraction or spatial projection fails due to unsupported backbone pooling or corrupt input dimensions, the system safely catches the error and degrades gracefully without failing the surrounding HTTP transaction.

\subsection{Content-Addressed Ephemeral Image Caching}
\label{subsec:cam_ephemeral_cache}

Computing CAM saliency synchronously on every prediction request would unnecessarily consume CPU cycles and bloat response payloads for automated clients that only require categorical predictions. Conversely, forcing the client to re-upload raw multi-megabyte image payloads whenever an operator requests visual explanation incurs substantial network latency and memory overhead.

To resolve this trade-off, the serving layer implements a content-addressed ephemeral image cache governed by \nolinkurl{ImageCacheProtocol} in \nolinkurl{src/taxon_vision/service/storage.py}, backed by an in-cluster Redis ephemeral instance (\nolinkurl{RedisImageCache}) with in-memory fallback (\nolinkurl{MemoryImageCache}):
\begin{enumerate}
    \item \textbf{Content Addressing via SHA-256:} Uploaded raw image bytes are hashed using SHA-256 to generate an immutable content digest (\texttt{image\_hash}).
    \item \textbf{Multi-Pod Split-Brain Mitigation:} Rather than isolating cached payloads within a single pod's heap, images are stored in a shared cluster Redis instance (\texttt{redis-ephemeral:6379}), ensuring that subsequent CAM attribution requests routed round-robin across replicas resolve the image payload seamlessly.
    \item \textbf{Bounded LRU and Rolling TTL Eviction:} The cache enforces a strict memory ceiling (\texttt{maxmemory 64mb} with \texttt{allkeys-lru}) and monotonic rolling time-to-live eviction (\texttt{image\_cache\_ttl\_seconds = 900.0}, or 15 minutes, refreshed upon access), configured via \nolinkurl{config/default_config.yaml}.
    \item \textbf{Zero Fast-Path Disk I/O:} Temporary images are never written to disk during the standard prediction path, avoiding unbuffered file I/O latency on high-throughput serving nodes.
\end{enumerate}

\subsection{Progressive-Disclosure Operator UI and Differential CAM}
\label{subsec:cam_progressive_disclosure}

The FastAPI serving runtime and HTMX dashboard operationalise this decoupled architecture through progressive disclosure:
\begin{enumerate}
    \item \textbf{Fast-Path Inference ($<15\text{ ms}$):} The synchronous prediction endpoints (\texttt{POST /ui/predict-htmx} and \texttt{POST /api/v1/predict}) execute the dual-output ONNX model, evaluate conformal prediction sets $\hat{C}(X)$, and compute epistemic telemetry (Shannon entropy and Helmholtz free energy compared against thresholds $\tau_{\text{OOD}}$ and $\tau_{\text{entropy}}$). The dashboard immediately renders the prediction card containing candidate probability bars and epistemic telemetry badges without waiting for saliency synthesis.
    \item \textbf{On-Demand Lazy Heatmap Synthesis (\texttt{/api/v1/explain}):} The CAM interface is embedded in a collapsible HTML5 \texttt{<details>} drawer. The client browser triggers an asynchronous HTMX request (\nolinkurl{hx-post="/api/v1/explain?image_hash=...&target_class_index=..."}) with the trigger condition \texttt{hx-trigger="toggle once"}, synthesising the heatmap overlay only when the operator actively opens the drawer.
    \item \textbf{Differential Multi-Candidate Inspection:} When an observation yields a non-singleton conformal prediction set (e.g., $|\hat{C}(X)| \in \{2, 3\}$), the drawer provides interactive candidate toggles. Operators can click individual competing taxa to dynamically inspect class-specific activation maps for contrasting hypotheses on the identical cached image. This allows taxonomists to verify whether the model attended to genuine diagnostic morphology (e.g., wing venation patterns or floral stamen structures) or spurious background correlation.
    \item \textbf{Fault-Tolerant Rendering:} If an expired hash or unsupported architecture triggers an exception during explanation, the endpoint returns an inline warning fragment (\nolinkurl{partials/cam_error.html}) at HTTP 200 for HTMX clients (and typed HTTP 422 for machine API consumers), ensuring that the operator dashboard remains fully functional and responsive.
\end{enumerate}
